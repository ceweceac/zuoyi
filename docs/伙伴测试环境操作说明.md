# 伙伴测试环境操作说明

## 环境边界

| 用途 | Git 分支 | 数据库与账号 | 能否直接改正式环境 |
|---|---|---|---|
| 正式环境 | `main` | 正式数据库、正式密钥 | 否，`main` 已保护，只能通过 Pull Request 合并 |
| 公共测试环境 | `qa-staging` | 独立测试数据库、独立后台账号 | 否，不连接正式数据库，也不启动钉钉机器人和群发任务 |
| 伙伴开发 | `partner/zhiqiandoris-qa` | 本机测试库，或公共测试后台 | 否，只能向 `qa-staging` 提交 Pull Request |

代码可以从测试分支合并到正式分支；数据库内容不能靠 Git 自动合并。QA 内容需要从测试后台导出“正式环境变更包”，由负责人审核、dry-run 后再导入正式库。

## 第一次在伙伴电脑上使用 Codex

先在 GitHub 接受 `ceweceac/zuoyi` 的仓库邀请，然后让 Codex 执行：

```bash
git clone https://github.com/ceweceac/zuoyi.git
cd zuoyi
git fetch origin
git switch --track origin/partner/zhiqiandoris-qa
```

可以直接把下面这段话交给 Codex：

> 只在 `partner/zhiqiandoris-qa` 分支修改代码和 QA 内容，不要切换或提交到 `main`。修改后运行项目测试，推送当前分支，并创建一个以 `qa-staging` 为目标分支的 Pull Request。不要提交 `.env`、数据库、密码或 API 密钥。

以后每次开始工作前先同步公共测试分支：

```bash
git fetch origin
git merge origin/qa-staging
```

如果出现冲突，让 Codex停下来逐项处理，不要使用强制推送覆盖远端。

## 后台登录与验证

公共测试后台使用伙伴专属账号。后台地址与初始密码由负责人单独发送，禁止写入 Git、聊天截图或代码文件。

需要验证尚未合并的代码时，伙伴也可以在自己电脑启动一套完整测试后台：

```bash
cp deploy/qa-workspace.env.example deploy/qa-workspace.env
# 在本机填写测试密码和随机密钥，禁止填写正式环境密钥
docker compose --env-file deploy/qa-workspace.env \
  -f deploy/docker-compose.qa-workspace.yml up -d --build
```

浏览器打开 `http://127.0.0.1:8081`。这套后台使用独立 Docker volume，不会读取或修改正式数据库。

## 合并顺序

1. 伙伴把 `partner/zhiqiandoris-qa` 推送到 GitHub。
2. 伙伴创建 `partner/zhiqiandoris-qa` → `qa-staging` 的 Pull Request。
3. 负责人审核并在公共测试后台验证，通过后合并到 `qa-staging`。
4. 需要上线时，负责人再创建 `qa-staging` → `main` 的 Pull Request。
5. 代码上线后，负责人从测试后台下载 QA 正式环境变更包，先 dry-run，再备份并导入正式数据库。

详细的 QA 数据审核和导入方法见 [`qa/PLATFORM.md`](../qa/PLATFORM.md)。
